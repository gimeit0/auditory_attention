## 一、总体结论

- 计划正确复用了 2b 管线（对齐 / 锚点 / 切片 / checkpoint / 评分），within-item 设计、inf 单点画法都与我们修过的 2b 一致，也诚实标注了"待核实"项。

## 三、⚠️ 需要调整的预期（基于我们的实测经验）

### 提醒 1（最重要）：混淆面板 Fig 2d 很可能栽在我们 2e 踩过的坑

- **已知事实**：我们的干扰是**随机抽取、未锚定 800 词表**。实测导致 2e 混淆率比论文低 **4–5 倍**：
  - 18.5% 的干扰句根本没有词表内的词；
  - −9dB 同性档，错误里只有 **9.7%** 是真·干扰入侵，其余 66.8% 是"第三类词"。
- 本计划 §2.4 的混淆度量**继承同一根因**：干扰片段中间词大多是 OOV，命中不了 → **混淆绝对值会贴地板**。
- **含义**：
  - 成功判据 #4 的**绝对量级大概率复现不出论文**。
  - 但有个利好细节：**干扰越多 → 词表内干扰词出现概率越高 → "更多干扰→更多混淆"的趋势方向可能仍能出来**（只是绝对值低）。
- **建议**：
  - Fig 2d **只当方向性结果**，绝对量级列为**已知局限**（延续 2e 的诚实说明），不为它返工。
  - 若真要复现混淆量级：需让干扰也**锚定词表中间词（对称构造）**——这是更大的改动，**本次不做**。

### 提醒 2：算力——约为 2b 的 2 倍，CPU 上跑不动

- 2b：600 × 6 SNR × 2 条件 ≈ 7,200 次推理，CPU 上各 ~6.5h。
- 本面板：600 ×（5 条件 × 5 SNR + 1 no-dist）≈ **15,600 次**，CPU 粗估 **13h+**（还遇到过休眠中断）。
- **缓存耳蜗图只能省 cue 那部分**；混音图每次都不同、省不掉。
- **结论**：这个面板基本"必须上 GPU（HAKUSAN）"。**准确率面板是稳的主交付物**，混淆面板次要/方向性。

## 四、几个小技术点（不影响大局，实现时注意）

1. **§3.1 多干扰混音最省事的实现**：把 N 个干扰 RMS 对齐后**求和成一个 masker**，再直接调现有的 `snr_scan.py:compose(snr)(target, masker)`（内部就是仓库的 `CombineWithRandomDBSNR`）——这天然就是"总掩蔽能量"归一，几乎不用写新混音逻辑。
2. **跨条件的干扰集合嵌套关系未指定**（two = one + 1？还是各自独立抽）。**独立抽**（每个 (target, 条件) 固定种子）即可，不是 blocker，但建议在 config 里写清。
3. **实际复用入口**（§4 第 1 步"定位复用模块"应指向这些）：
   - `align_words.py` — 对齐 / 规范化 / 锚点判定（`process_clip` / `normalize_token` / `find_anchor_candidates`）
   - `build_anchor_first.py` — 说话人抽样 / 锚点优先配对（可扩为多干扰抽样）
   - `slice_stimuli.py` — 切片（`load_44k` / `slice_centered` / `slice_middle`）
   - `snr_scan.py` — 混音（`compose`）+ 模型加载（`build_model`）+ 评测循环骨架
4. **评分口径**：计划用 exact（预测词==目标中间词），与我们 2b 一致；论文用 lenient，但对我们数据 exact≈lenient，沿用 exact 即可。

## 五、建议的执行顺序（调整后）

1. **先做准确率面板**（稳）：no-distractor / one / two / four / babble × 5 SNR + inf 单点。
   - 预期趋势会复现：SNR↑准确率↑、干扰越多越难、inf 收敛到 ~88%。
2. **混淆面板作为次要产出**：同一批预测顺手算，但**标注为方向性 + 绝对量级偏低（已知局限）**。
3. **直接规划到 GPU（HAKUSAN）上跑**：CPU 不现实；这与当前搭超算环境同一条线。
4. **跑前补"待核实"**：多源 SNR 归一、babble talker 数、样本量/SNR 档——从论文 PDF/OSF 确认后再锁 config（默认值 total_masker / babble=8 是合理起点）。
